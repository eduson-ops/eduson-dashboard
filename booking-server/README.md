# Сервер бронирования Eduson

Сервер хранит бронирования, расписания, пользователей, отчёты, историю изменений и очередь синхронизации. Доступ определяет серверная роль пользователя.

```text
Браузер -> nginx -> Node.js -> PostgreSQL, схема eduson_booking
                             +-> очередь -> Google Sheets, если включено
/dashboard/ -> адаптер -> данные сервера + прежние Google-таблицы
```

| Роль | Основная работа |
| --- | --- |
| КЦ (`call_center`) | Создать запись в доступном интервале |
| Подтверждение (`confirmation`) | Подтвердить запись, отменить или восстановить её |
| Сейл (`sales`) | Работать со своими назначениями, провести урок, заполнить отчёт |
| Администратор (`admin`) | Настроить пользователей и расписания, проверить загрузку, аудит и очередь |

## Локальный запуск

Нужен Node.js 22 или новее. Зависимости зафиксированы: `pg` 8.23.1 и `@electric-sql/pglite` 0.5.15.

Выполните из корня репозитория:

```sh
npm ci
npm test
npm run demo
```

Откройте `http://127.0.0.1:4180/`. Демо использует синтетические записи и сохраняет изменения в `.booking-demo/`. Повторный запуск сохраняет историю. Данные каталога не входят в релиз.

| Учётная запись | Роль |
| --- | --- |
| `admin@demo.local` | Администратор |
| `kc@demo.local` | КЦ |
| `confirm@demo.local` | Подтверждение |
| `sale@demo.local`, `sale2@demo.local`, `sale3@demo.local` | Сейлы |

Пароль **только для демо**: `EdusonDemo2026!`. Эти учётные записи нельзя переносить в production. Демо не запускает фоновые задачи и не пишет в Google. Аналитика может читать существующие Google-таблицы.

Обычный `npm start` требует `DATABASE_URL`. Приложение не загружает `.env` автоматически. Передайте переменные окружения либо используйте Node:

```sh
node --env-file=/absolute/path/to/local-booking.env booking-server/server.mjs
```

Для отдельного локального просмотра можно убрать `DATABASE_URL` и явно задать `BOOKING_EMBEDDED=1`. Тогда PGlite хранит данные в `.booking-data/` или `BOOKING_DATA_DIR`. Этот режим не рекомендуется для production.

## Маршруты и вход

`/` и `/booking/` открывают новое бронирование. `/dashboard/` открывает прежнюю аналитику с адаптером данных. `/health` подтверждает ответ процесса; отдельный запрос к БД этот маршрут не выполняет.

Пользователь входит по почте и паролю. Общего кода доступа и выбора роли перед входом нет. Сервер хранит хеш пароля и сессию. Изменения требуют CSRF-токен. Сессия действует восемь часов.

`BOOKING_ADMIN_EMAIL` и `BOOKING_ADMIN_PASSWORD` создают первого активного администратора, если его ещё нет. `BOOKING_ADMIN_NAME` задаёт имя. Эти параметры не сбрасывают пароль существующего администратора. После создания удалите bootstrap-параметры из рабочего окружения.

За reverse proxy задайте точный `BOOKING_PUBLIC_ORIGIN`. Для production сначала установите и проверьте TLS. Затем задайте HTTPS origin и `BOOKING_SECURE_COOKIES=1`. Не включайте secure cookies на HTTP: браузер не отправит такую сессию.

По умолчанию лимит входа использует IP TCP-соединения и игнорирует `X-Forwarded-For`. За локальным nginx этот IP общий для всех клиентов. Без настройки доверия десять неудачных входов одного клиента могут заблокировать вход команды на 15 минут.

После проверки локального nginx задайте `BOOKING_TRUST_PROXY=1`. Backend должен слушать только `127.0.0.1`, а nginx — передавать `X-Forwarded-For $proxy_add_x_forwarded_for`. Сервер доверяет заголовку только при loopback peer. Он использует последний элемент цепочки, если `node:net.isIP` подтверждает IP. Для другого peer или невалидного значения сервер использует IP TCP-соединения. Автоматического доверия заголовкам нет.

## Данные, аналитика и Google Sheets

Сервер применяет `schema.sql` при открытии БД. Схема приложения — `eduson_booking`. Версия миграции 1 расширяет возрастной диапазон до 1–18 лет. Версия 2 разрешает неизвестные признаки ПК и участия родителя только у импортированных записей. Поэтому первый запуск с реальной `DATABASE_URL` уже меняет БД.

Сервер не импортирует автоматически старые записи из Pages или Google Sheets. До переключения нужна отдельная сверка источников и пробный перенос на копии данных.

Стабильный `Booking ID` связывает запись сервера с проекцией в таблице. Он предотвращает повторную строку после неопределённого результата записи. Совпадение CRM само по себе не означает совпадение уроков. Строки старой истории без `Booking ID` сохраняются отдельно.

Адаптер аналитики заменяет данные с тем же `Booking ID`, сохраняет старую историю и получает изменения через SSE `/api/events`. При сбое API адаптер использует прежний источник и показывает состояние интеграции. Восстановление записи снимает её текущую отмену. Факт отмены и её автор сохраняются в аудите и архивных данных.

`amountNet` — сумма из отчёта об уроке. Она не подтверждает оплату. Выручка и факт оплаты в прежней аналитике по-прежнему берутся из листа «Оплаты».

Запись в Google выключена по умолчанию. Для включения нужны все три runtime-параметра:

```text
BOOKING_SHEETS_SYNC=1
GOOGLE_SERVICE_ACCOUNT_PATH=/absolute/path/outside-webroot/service-account.json
BOOKING_SHEET_ID=<согласованный ID таблицы>
```

Храните JSON сервисного аккаунта вне репозитория и webroot. Дайте пользователю `eduson-booking-platform` только чтение файла. Не вставляйте JSON в HTML, `.env.example` или исходники.

Worker обрабатывает устойчивую очередь раз в 15 секунд. Сначала он обновляет проекцию расписания и мест. Затем он обрабатывает до восьми заданий записей за проход. Он проверяет заголовки перед записью и повторяет временные ошибки с задержкой. После восьми попыток задание остаётся с ошибкой. Состояние доступно администратору через `/api/sync`.

| Лист | Диапазон | Связь с записью |
| --- | --- | --- |
| `Расписание` | A:C | Управляемая пара: дата и точное имя менеджера |
| `Слоты` | A:E | Повторные строки задают резерв; `Booking ID` в E |
| `Booking VDS` | A:L | ID в A |
| `Ответы формы` | A:P | 14 прежних полей, `Booking ID` в O, `Test flag` в P |
| `Отмены` | A:J | 8 прежних полей, `Booking ID` в I, `Booking status` в J |
| `Подтверждения` | A:F | 4 прежних поля, `Booking ID` в E, `Кто подтвердил` в F |
| `Оплаты` | A:K | 9 прежних полей, `Payment ID` в J, `Booking ID` в K |

Отдельная оплата также попадает в согласованный реестр зачисления учеников. В нём остаются 43 прежних столбца. `Payment ID` занимает AR, `Booking ID` — AS. Повторная доставка не перезаписывает ручную обработку уже созданной строки реестра.

Отчёт о проведённом уроке не создаёт оплату. Урок, оплата и зачисление имеют разные факты и задания доставки. Сначала транзакция сохраняет факт и очередь в PostgreSQL. Затем worker независимо доставляет каждое задание. Тестовый урок получает `Test flag=true` и исключается из аналитики и начислений.

Листы и первые бизнес-заголовки должны уже существовать. Worker добавляет только пустые служебные заголовки после проверки содержимого столбцов. Чужой заголовок, занятый служебный столбец или повторный ID блокируют запись. При восстановлении worker сохраняет факт отмены и меняет `Booking status` на `restored`.

## Условия выпуска

Шаблоны в `deploy/` подготовлены для отдельного сервиса. Они не развёрнуты и не включают автозапуск.

Действующая установка использует `eduson-booking-platform.service`, PostgreSQL `eduson_booking_platform` и каталог `/opt/eduson-booking-platform`. Прежний сервис остановлен, его файлы сохранены. SSH доступен через Wi-Fi в обход VPN. GitHub Pages публикует ветку `booking`. Шаблоны не заменяют инвентаризацию и проверку отдельного релиза.

Последовательность допуска к переключению:

1. Владелец подтверждает сервер, домен, БД, текущие сервисы, vhost, порты, пользователей и источники данных.
2. Оператор сохраняет действующие конфигурации и согласованные резервные копии. Он проверяет восстановление на изолированной БД.
3. Оператор применяет миграцию и пробный перенос только к копии. Он сверяет записи, отчёты, отмены, назначения и стабильные ID.
4. Оператор проверяет отдельный релиз через loopback, PostgreSQL по TCP и четыре роли. Запись в Google остаётся выключенной.
5. Владелец согласует маршруты и переключение. Оператор проверяет TLS, origin, cookies, SSE и `nginx -t`. После проверки loopback nginx он задаёт `BOOKING_TRUST_PROXY=1` и проверяет раздельные лимиты входа клиентов.
6. После переключения оператор проверяет пользовательский сценарий. Синхронизацию включают отдельно после проверки копии Google-таблицы и очереди.

Пока условия не выполнены, действующие сервисы, Pages и vhost остаются без изменений.

## Изолированная установка

Новый каталог: `/opt/eduson-booking-platform/releases/<release>`. Символическая ссылка `/opt/eduson-booking-platform/current` указывает на проверенный релиз. Сохраните предыдущую цель ссылки для отката.

Код принадлежит оператору или root. Непривилегированный системный пользователь `eduson-booking-platform` получает только чтение кода. Рабочее окружение хранится в `/etc/eduson-booking-platform.env` с владельцем `root:eduson-booking-platform` и правами `0640`. Секреты не входят в каталог релиза.

Используйте `.env.example` как перечень настроек. Замените конфигурационные маркеры реальной строкой PostgreSQL после инвентаризации. Пользователь БД должен работать только с согласованной БД и схемой `eduson_booking`. Для миграции нужны права создания схемы, таблиц и изменения ограничений.

Установите зависимости через `npm ci` внутри нового релиза. Проверьте реальный путь к Node 22+. Затем адаптируйте `deploy/eduson-booking-platform.service`. Он запускает production entrypoint напрямую и требует файл окружения. `BOOKING_EMBEDDED` должен оставаться выключенным.

Проверьте unit через `systemd-analyze verify` на целевом хосте. После допуска запускайте только новый `eduson-booking-platform.service`. После проверки включите автозапуск нового сервиса. Отключите автозапуск прежнего booking-сервиса при переключении.

`deploy/nginx.conf.example` — фрагмент для согласованного отдельного `server {}`. Он проксирует корень, аналитику и API на `127.0.0.1:4180`. SSE отключает буферизацию и использует тайм-аут дольше heartbeat. Не заменяйте существующий vhost этим файлом. Реальные сертификаты и HTTPS-редирект настраивают только после установки TLS.

Проверьте закрытый внешний доступ к backend и передачу реального IP последним элементом `X-Forwarded-For`. Только после этого включите `BOOKING_TRUST_PROXY=1`. При прямом доступе без проверенного proxy оставьте `0`.

## Резервная копия и откат

Перед миграцией и переключением владелец определяет полный набор источников. Копия только `eduson_booking` не покрывает другие схемы, старую БД или Google-таблицы. Сохраните их отдельно согласно инвентаризации. Копии содержат персональные данные; ограничьте доступ и проверьте срок хранения.

Для уже существующей схемы нового сервиса пример команд выглядит так. Переменные должны указывать на проверенные БД и пути. `BOOKING_RESTORE_URL` обязан вести в пустую изолированную БД для проверки восстановления.

```sh
pg_dump --dbname="$DATABASE_URL" --format=custom --schema=eduson_booking --file="$BOOKING_BACKUP_PATH"
pg_restore --list "$BOOKING_BACKUP_PATH"
pg_restore --dbname="$BOOKING_RESTORE_URL" --no-owner --no-privileges "$BOOKING_BACKUP_PATH"
```

Владелец отдельно восстанавливает согласованные роли и права. Проверьте количество записей, отчёты, аудит, очередь и вход после восстановления. Если схема ещё не создана, сначала сохраните существующие источники; пустая новая схема не заменяет их резервную копию.

При откате остановите новый сервис и запись в Google. Верните предыдущую цель `current` и согласованную конфигурацию маршрутов. Перед возвратом старого кода проверьте совместимость схемы. Не восстанавливайте старую копию поверх новых записей: сначала сохраните изменения после переключения и согласуйте их перенос. Выполните smoke-check прежнего маршрута и четырёх ролей.

## Границы проверки

Локальные тесты БД используют PGlite. Они проверяют транзакции, ограничения, сохранение данных, миграцию и версии записей. Это не подтверждает подключение к отдельному PostgreSQL по TCP.

Тесты синхронизации используют имитацию Google. Действующая установка также прошла проверку четырёх ролей, TLS, очереди Google и восстановления резервной копии. Для изменений v3 выполнен отдельный прогон PostgreSQL по TCP на копии рабочей базы. `/health` сам по себе не подтверждает пользовательский сценарий и доставку нового вида отчёта.

## Перенос прежних записей

`legacy-import.mjs` переносит согласованный закрытый JSON-снимок SQLite и Google Sheets. Сначала проверьте его без записи:

```sh
node booking-server/legacy-import.mjs --snapshot /private/legacy-snapshot.json
node --env-file=/etc/eduson-booking-platform.env booking-server/legacy-import.mjs --snapshot /private/legacy-snapshot.json --apply --credentials-out /private/staff-access.json
```

Файл доступов создаётся один раз с правами 0600. Пароли не попадают в stdout. Повторный импорт проверяет исходные отпечатки и отказывается перезаписывать отличающуюся базу.

Импорт сохраняет исходные ID, время, сырые сведения и аудит. Старый статус `active` означает запись, а не подтверждение. Совпадающее подтверждение требует точного CRM, времени слота, причинного диапазона времени и полного имени менеджера. Неизвестный итог прошедшего занятия уточняет администратор. Такой урок не отменяется автоматически.

Смешанная ёмкость старых слотов сохраняется отдельно для каждого интервала. Изменение сотрудника после прошедшего урока не удаляет историю расписания. Worker меняет только управляемые пары менеджер/дата; чужие строки и прежняя история сохраняются.

Действующий GitHub Pages dashboard открывает новый букинг по ссылке. Прежний `booking-ui.js` больше не отправляет записи в Apps Script. Аналитика нового сервиса доступна на `/dashboard/`.

## Букинг v3

КЦ работает через три шага: формат, время и контакты. Свободные места берутся из расписания и проверяются повторно при записи. Расписание показывает 14 дней от текущей даты. Копирование недели объединяет часы. Атомарное сохранение меняет только переданные даты и проверяет версии всех дней.

Подтверждение автоматически выбирает подходящего методиста. Система сначала заполняет основные места, затем резерв. Возрастные ограничения сохраняют свободные места для учеников, которым подходят не все методисты. Каждый показатель часовой статистики открывает соответствующий список.

Начисления закрепляются за первым сотрудником подтверждения: 100 ₽ за подтверждение, 200 ₽ за проведённый урок. Каждый компонент начисляется один раз. Месячный период использует московское время события. Отмена не удаляет выполненную работу подтверждения. Тесты не создают начислений.

`migration-v3.mjs` предоставляет `migrateV3(db, input, options)`. Предварительный прогон возвращает отпечаток базы и безопасные счётчики. Применение требует этот отпечаток под общей блокировкой. Реестр исходных ID защищает повторный импорт. Расписание объединяется по сотруднику, дате и часу. Прежние резервы сохраняются. Для новых будущих часов резерв задаётся явной политикой.

Для потерянных ноябрьских записей источником служит AmoCRM. Отсутствие записи в Rubitime или Booking VDS не опровергает сделку. Rubitime ID сохраняется отдельно; его поле заказа не заменяет доказательство связи с CRM. Архив с неизвестным исходом сохраняется без выдуманной посещаемости и без календарной занятости. Сырые выгрузки содержат персональные данные и хранятся вне Git и публичного релиза.

## Уведомления и общий календарь

`BOOKING_SLACK_CONFIG_PATH` указывает на закрытый JSON вне webroot. В нём находятся `enabled`, `token`, `teamId`, `summaryChannelId`, `baseUrl` и `staffMap`. Соответствия `staffMap` задаются точными ID пользователей букинга и Slack. Проверка провайдера отклоняет другую команду, удалённого пользователя и бота. Файл должен читать только владелец и группа сервиса.

При включении сервер сохраняет тихую границу до приёма пользовательских действий. Прежние назначения и завершённые уроки не вызывают массовых личных сообщений. Новое назначение получает текущий менеджер. Передача уведомляет прежнего менеджера. Тестовые и архивные записи исключены.

Через 15 минут после конца урока бот просит указать фактический итог. Для завершённого урока он просит недостающий отчёт. Позднее завершение переносит срок напоминания. Сохранённый отчёт, отмена и передача снимают устаревшее сообщение. Напоминания ограничены последними 72 часами; бот не меняет статус урока и не создаёт посещаемость.

Почасовая карточка обновляется в одном сообщении. PostgreSQL хранит задания, адресатов, ограничения скорости и подтверждения доставки. После неопределённого результата нового сообщения автоматическая повторная отправка останавливается. Известное сообщение можно обновить повторно. Администратор видит проблемы через `/api/notifications/status`; секреты и тексты сообщений этот маршрут не возвращает.

Во время совместной работы с прежним источником задайте отдельные `BOOKING_SCHEDULE_SHEET_NAME` и `BOOKING_SLOTS_SHEET_NAME`. Создайте листы с прежними бизнес-заголовками; у слотов добавьте `Booking ID` в E1. Старые листы продолжает обслуживать прежний процесс. После изменения назначения листов пометьте проекцию календаря ожидающей отправки и сверьте полный набор часов, мест и занятости. Общий worker обрабатывает максимум четыре задания Google за цикл, чередуя записи и операционные отчёты.
