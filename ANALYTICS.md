# Правила аналитики

Дашборд читает существующие Google Sheets. Числа рассчитываются JavaScript-функциями, без LLM. Модель фактов — `analytics-core.js`, загрузка — `dashboard-load.js`, общие фильтры и главная — `dashboard-analytics.js`, остальные представления — `analytics-views.js`.

## Период и показатели

Период един для главной, аналитики, карточек менеджеров и копируемой сводки. Даты относятся к Москве. По умолчанию выбран сегодня; недели начинаются в понедельник. Личный режим имеет приоритет над фильтром менеджера.

| Показатель | Расчёт |
| --- | --- |
| МК | Отчёты об уроках + первичные оплаты без отдельного отчёта МК; одна оплаченная сделка добавляет один МК |
| Оплат | Положительные платежи на дату оплаты |
| Выручка | Сумма платежей и отрицательных корректировок на дату оплаты |
| Конверсия | Оплаты периода / МК периода × 100% |
| Средний чек | Выручка / число положительных оплат |
| Выручка / МК | Выручка / МК периода |
| Доходимость по отчётам | МК / (МК + отчёты об отменах) × 100% |

При нулевом знаменателе показан прочерк. Конверсия потоков может быть выше 100%: платежи и уроки периода не обязательно относятся к одним сделкам. Переключатель продлений меняет состав платежей во всех финансовых представлениях. Месячный план сравнивается с фактом всего месяца независимо от выбранного периода; личный план не выводится из равной доли общего.

Отмена датируется отправкой отчёта, поскольку дата отменённого урока отсутствует. Поэтому доходимость по отчётам не является точной исторической воронкой записанных клиентов. «Слоты» — обновляемый снимок записей, а доступность менеджеров — отдельное расписание; их нельзя использовать как историческое число проведённых МК.

## Связь данных

Обе формы достоверны: сейл может сообщить о проведённом МК через отчёт об уроке или через первичную оплату. Если по точному CRM ID уже есть отчёт МК, дополнительный урок из оплаты не создаётся. Дата из отчёта МК сохраняется, даже если оплатили позже. При нескольких отчётах одной сделки они сохраняются, а привязка платежа к конкретному уроку остаётся неоднозначной.

Если отчёта МК нет, первая положительная первичная оплата подтверждает один оплаченный МК. Его дата берётся из оплаты и явно помечена в журнале; время, возраст и канал не выдумываются. Поиск первой оплаты идёт по всей доступной истории до фильтрации периода. Последующие платежи одной сделки сохраняют деньги и количество оплат, но не добавляют МК. Продления и отрицательные корректировки не создают уроков. При разных менеджерах в первичных оплатах одной такой сделки МК остаётся без назначенного менеджера с диагностикой; деньги остаются у менеджеров платежей.

Без распознанного CRM ID платёжные отчёты не объединяются: каждый положительный первичный отчёт подтверждает МК со ссылкой на исходную строку и замечанием о CRM. Неизвестные менеджеры входят в общие итоги; пустое имя имеет отдельный фильтр. Для полного количества МК и конверсии требуется успешное чтение обеих форм.

Без постоянного ID записи одинаковые строки не удаляются автоматически. Возможные повторы, ошибочные суммы/даты и ссылки видны в разделе проверки данных; журналы ведут к исходным строкам. Некорректная сумма не превращается в ноль. Деньги хранятся в копейках.

Повторные покупки считаются по CRM-сделкам. Доход на сделку за доступную историю не называется клиентским LTV. Будущие месяцы когорт не показываются нулями; текущий месяц отмечается незакрытым.

## Загрузка и сохранение

Неудачное чтение сохраняет прошлый снимок в памяти, но зависимые показатели не выдаются за текущие. Проверяются HTTP-статус, структура CSV и значимые заголовки. Параллельные обновления объединяются в один запрос; новая модель применяется после завершения чтения всех источников.

Сохранение доступности проверяется полным совпадением всех дат и часов менеджера с повторно прочитанной таблицей. POST без доступного ответа не считается подтверждением. При неопределённом результате повторная кнопка читает источник, не повторяет запись; черновик и неопределённая попытка сохраняются в браузере. Отмена изменений также требует полного подтверждения. Автоматического снятия такой блокировки нет: непрозрачный старый запрос может завершиться позднее.

## Проверка

Запуск: `node --test tests/*.test.mjs`. Тесты охватывают модель, реальную интеграцию загрузки/фильтров/представлений, CSV, резервы и подтверждение сохранения. Они используют вымышленные данные и не пишут во внешние системы. Проверка реальной серверной записи и банковская сверка платежей — отдельные операции.
